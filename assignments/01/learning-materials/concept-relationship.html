Agent × 上下文 × Skill —— 三个概念的关系

2. 上下文如何影响 Agent 的工作

上下文窗口是 Agent 的"工作台大小"——它直接决定 Agent 能做多复杂、多长的任务。

2.1 上下文决定 Agent 的"视野"

  • 视野限制任务长度：每轮 ReAct 循环的"思考→行动→观察"结果都回写进上下文。多步任务的 token 消耗是累加的——50 步的 Agent 任务轻松吃掉 50K+ token。
  • 视野限制记忆：超过窗口的早期指令、用户偏好、工具结果对 Agent 直接"消失"。这是 Agent 跑长任务时"失忆"和"重复试错"的主因。
  • 视野影响质量：Lost in the middle 现象——关键事实放在长上下文中段被忽略的概率显著升高。

2.2 Agent 对上下文的"反作用"

  • Agent 主动管理上下文：成熟 Agent 会在窗口快满时调用"摘要压缩"工具，把历史浓缩成更短的表示。
  • Agent 决定哪些信息进上下文：通过 RAG 检索、工具结果过滤，只把当前步最相关的内容塞进窗口。
  • Agent 把"目标"反复写回窗口：避免目标感在长任务中丢失。
工程含义：设计 Agent 时，"上下文预算分配"和"任务规划"是同一件事。任务越复杂，越要主动设计"何时压缩、何时重读目标、何时丢弃旧观察"。

3. Skill 如何沉淀可复用的任务知识

Skill 是连接"人类经验"和"Agent 行为"的桥梁——它把分散在各处的"该这样做"沉淀成可版本化、可分发、可按需加载的能力单元。

3.1 沉淀的对象：从"对话"到"资产"

沉淀前沉淀后（Skill）
每次贴一大段 prompt：
"用我司模板写周报，3 段式……"		SKILL.md：
description 触发 + 正文规定模板 + examples/ 给出样本
团队代码评审标准散落在 Wiki / 群聊code-review-skill：
新人+老员工+AI 评审都按同一标准出
反复调整 system prompt 试图让 AI 稳定输出针对性 Skill：
触发即加载、关闭即释放，主 system prompt 保持稳定
脚本命令记在 shell history 或 READMEscripts/validate.sh：
AI 在 Skill 指引下调用，无需人记命令

3.2 沉淀的机制：四大属性

  • 可版本化：文件夹结构天然适合 Git，可回滚、可 diff、可 review。
  • 可分发：同 Skill 在 Claude.ai / Claude Code / API 通用；可放到 marketplace（Anthropic 2025-12 推出官方目录）。
  • 可复用：一次写好，多个 Agent、多个项目、多个团队成员使用。
  • 不污染主上下文：未触发时不占窗口——这是 Skill 区别于"长 system prompt"的关键。

3.3 Skill 与"上下文管理"的协同

Skill 的设计本身就是一种"上下文管理"：

如果所有团队知识都塞进 system prompt：
  → 每次对话都吃满 token
  → 真正任务相关的内容被挤压
  → 模型注意力分散，输出质量下降

如果用 Skill 拆分：
  → 系统 prompt 保持精简（只设全局规则）
  → 各专题能力按需加载（命中才占窗口）
  → 上下文利用率高、响应更快、cost 更低
沉淀飞轮：人写 Skill → Skill 被 Agent 高频使用 → 发现 Skill 的不足 → 修改 Skill → 沉淀更稳定的能力。Skill 是"AI 团队的代码化文档"。

4. 三个概念协同的一个完整例子

以"自动给新员工生成入职检查清单"为例，看三者怎么配合：

  1. 用户 → Agent：HR 跟 AI 助手说"给新同学张三代办入职清单，岗位是数据分析师"。
  2. Agent 读上下文：上下文里有系统提示（"你是 HR 助手"）、历史对话、当前用户输入。
  3. Agent 匹配 Skill：发现任务匹配 onboarding-checklist Skill 的 description（"为新员工生成入职流程"），把它的 SKILL.md 加载进上下文。
  4. Skill 指引执行：SKILL.md 规定要调用 HR 系统 API、读取岗位模板、生成按部门差异化的清单。
  5. 工具结果回写上下文：HR API 返回结果约 800 token，岗位模板约 400 token，都写进上下文（窗口占用 ↑）。
  6. Agent 综合推理：基于"系统提示 + Skill 指引 + 工具结果 + 用户输入"生成最终清单。
  7. 窗口管理：若这是长会话，Agent 在上下文快满时主动压缩历史，保留"张三是数据分析师"这一关键信息。

整个过程，Skill 解决了"怎么做"，上下文解决了"看到什么"，Agent 解决了"做不做、按什么顺序做"——三者缺一不可。

5. 关系速查表

关系方向内容失效条件
Agent → 上下文读写Agent 在上下文里推理；每轮结果回写 窗口溢出 → 早期指令丢失 → Agent 失忆
上下文 → Skill加载 / 释放命中时加载，未命中不占 描述写得不好 → 永远不命中 / 误触发
Agent → Skill触发Agent 读 description 决定是否调用 Skill 太多 → 路由变慢 / 误匹配
Skill → 上下文注入加载后占窗口 token Skill 内容过大 → 挤占任务 token
Agent → 上下文 → Skill协同Agent 决策、上下文提供视野、Skill 注入能力 三者任一设计失衡 → 系统不稳定

6. 常见误解与澄清

  • 误解："Agent 就是 Skill 的组合"。澄清：Skill 只是 Agent 可调用的能力之一；Agent 还有记忆、规划、工具调用等"自有"组件，Skill 是外挂的扩展。
  • 误解："上下文越大 Agent 越强"。澄清：上下文扩大的同时计算成本 O(N²) 增长、Lost in the middle 加剧；要做的是"有效信息密度"，不是"无限堆 token"。
  • 误解："Skill 等于 prompt 模板"。澄清：Skill 含目录结构、YAML 元数据、可执行脚本；按需加载且不污染主上下文——这是 prompt 模板做不到的。
  • 误解："三个概念可以分开学"。澄清：它们互为约束：没有上下文就没有 Agent 推理；没有 Skill 就只能把所有指令塞进 prompt（吃 token）；没有 Agent，Skill 只是静态文档。

7. 自测题

Q1：为什么"上下文大小"直接限制 Agent 能跑多复杂的任务？

参考答案：Agent 每一步"思考/观察"结果都要回写进上下文。多步任务 token 累加，超过窗口后早期指令/记忆对模型直接"消失"，Agent 会"失忆"或"重复试错"。窗口越大、压缩/检索策略越好，Agent 能跑的任务越长。

Q2：Skill 为什么说"沉淀可复用的任务知识"？举一个具体例子。

参考答案：因为 Skill 把"做事方法"（步骤、模板、脚本、判定标准）从 prompt 里抽出来做成文件夹，可以版本控制、跨项目共享、按需加载。例如把"团队 PR Review 规范"做成 code-review-skill，新人、老员工、AI 评审都按同一标准出稿，避免每次重新说明。

Q3：如果 Agent 跑长任务时频繁"重复试错"，最可能是哪个概念出问题？怎么修？

参考答案：最可能是上下文出问题：窗口快满导致早期目标/约束被截断。修法：(1) 主动做上下文摘要压缩；(2) 把"任务目标"反复注入；(3) 拆任务为子任务；(4) 用 Skill 减少每次都贴的长 prompt。

Q4：把"团队所有经验"全塞进 system prompt，会带来什么后果？用 Skill 怎么解？

参考答案：后果：每次对话都吃满 token，模型注意力被无关内容分散，关键指令被淹没，cost 暴涨，输出质量反而下降。用 Skill 解决：把团队经验按"专题"切成多个 Skill（如品牌规范、代码评审、客户话术），各 Skill 保持精简，由 Agent 按 description 匹配后按需加载，主 system prompt 保持稳定简短。

Q5：请用一句话讲清 Agent / 上下文 / Skill 三者的关系。

参考答案：Agent 是"做决定的大脑"，上下文是它"看到的工作台"，Skill 是它"按需调用的工具书"——Skill 在需要时被加载进上下文供 Agent 使用，三者协同完成复杂任务。
