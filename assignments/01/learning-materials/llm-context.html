大模型的上下文（Context Window）概念学习资料

概念 大模型 / Transformer 生成于 2026-09-04 · 使用 concept-study-pack Skill

学完这份资料，你将能用自己的话解释"上下文窗口"是什么、为什么它有上限、它和系统提示、RAG、长期记忆的关系，以及实际工程中常见的"长上下文陷阱"。

1. 学习目标

  1. 用自己的话解释"上下文窗口（context window）"是什么、它的硬性边界在哪。
  2. 说明上下文窗口的工程上限来自 Transformer 自注意力机制的 O(N²) 计算复杂度。
  3. 区分上下文窗口、系统提示（system prompt）、RAG、长期记忆四种信息来源。
  4. 识别"Lost in the middle"现象及其对长上下文设计的影响。
  5. 理解 KV-Cache 机制及其对显存和延迟的影响。

2. 核心问题

  1. 为什么大模型一次只能"看"有限长度的输入？这背后是软件限制还是数学限制？
  2. 把上下文从 4K 扩到 128K 甚至 1M 到底付出了什么代价？
  3. 为什么有时把关键信息放在中间，模型反而"看不见"？
  4. 为什么多轮对话久了模型会"失忆"？这是 bug 还是设计？
  5. 系统提示、RAG、长期记忆、上下文窗口这四个词到底怎么区分？

3. 个人解释

一句话：上下文窗口是大模型一次推理时能"同时看到"的最大 token 数，是 Transformer 自注意力机制的硬性工程边界——超过它的内容模型直接看不见，不会"记住"，更不会"理解"。

用一个日常类比：你正在读一本悬疑小说，但你的短期记忆只够装 50 页。当你读到第 80 页时，第 1 章里的关键线索已经从你脑子里掉光了——除非有人提醒你。上下文窗口就是模型的那个"短期记忆容量"，单位是 token（一个 token 大约等于 0.75 个英文单词或 1-2 个汉字）。

这个"窗口"为什么不能无限大？因为 Transformer 在每一层都要让当前 token 和前面所有 token 做一次"相互打量"——这叫自注意力。如果窗口里有 N 个 token，单层就要算 N×N 次关系。N 翻倍，计算量变成 4 倍；N 变成 10 倍，计算量变成 100 倍。这就是 O(N²) 的二次方增长，是数学硬约束，不是加几块 GPU 就能解决的事。

因此所有号称"百万上下文"的模型，本质上都是在用 KV-Cache、量化、稀疏注意力等技巧，让用户在算力预算内勉强看到更多 token——而看不到的部分，对模型来说就是不存在。

4. 核心机制

4.1 Token：模型看到的最小单位

模型不直接读文字，先把文字切成 token——可能是整词、子词、符号或标点。

"unbelievable"  →  ["un", "believ", "able"]   // 3 个 token
"大模型上下文"    →  ["大", "模型", "上下", "文"]  // 4 个 token

上下文窗口的大小是按 token 数 算的，不是字数。模型先 tokenize，把 token 映射成高维向量（embedding），这些向量必须全部装进上下文窗口。

4.2 自注意力：为什么是 O(N²)

Transformer 用"自注意力"让每个 token 和窗口内其他所有 token 算一次关系分数：

对于 N 个 token：
Q = N × d    (Query 矩阵)
K = N × d    (Key 矩阵)
V = N × d    (Value 矩阵)
Attention = softmax(Q × Kᵀ / √d) × V    // Q × Kᵀ 是 N×N 矩阵
窗口 N每层注意力运算量
1,000约 100 万次
8,000约 6,400 万次
128,000约 164 亿次
1,000,000约 1 万亿次

这就是为什么上下文窗口是硬性架构边界，不是软件开关。

4.3 因果掩码（Causal Mask）：解码器只看到"过去"

GPT/Claude 这类自回归模型用因果掩码，让 token i 只能看到位置 ≤ i 的 token。矩阵上三角被"遮住"：

绿色=可见（左侧含自身），黄色=被掩码（不能看未来）。生成 T4 时只能基于 T1/T2/T3。

4.4 KV-Cache：长上下文的显存代价

每生成一个新 token，都要重新算前面所有 token 的注意力。KV-Cache 把已算过的 K/V 张量缓存下来，节省重复计算。但缓存大小随窗口线性增长，吃 GPU 显存。窗口翻倍，KV-Cache 显存也翻倍；这和注意力的二次方增长叠加，决定了上下文不可能无限扩展。

4.5 "Lost in the Middle"：长上下文的隐形陷阱

研究发现（Liu et al., 2023），当上下文变长，模型对位于中间位置的信息关注度明显下降，对开头和结尾的信息记得更牢（primacy bias + recency bias）。这意味着——把关键信息塞到长上下文的中间反而是最不靠谱的做法。

5. 应用场景

  1. 多轮对话与"长会话失忆"
    谁在用：所有对话式产品（ChatGPT、Claude、Gemini、文心一言）。
    解决什么：让模型在一次会话内持续跟随用户上下文。
    效果与陷阱：当对话累计超过窗口大小，模型会丢失早期指令；产品通常用"摘要压缩"或"短期记忆模块"兜底。
  2. 长文档问答 / 阅读（Claude 200K、GPT-4o 128K）
    谁在用：法律合同分析、论文综述、代码库理解。
    解决什么：把整本 PDF / 整个代码仓库塞进上下文，直接提问题。
    效果：可处理 500 页文档；但要注意"Lost in the middle"，关键条款最好放首尾。
  3. RAG（检索增强生成）
    谁在用：企业知识库、智能客服、技术文档助手。
    解决什么：把百万级文档拆 chunk 存入向量库，提问时只把最相关的若干 chunk 塞进上下文。
    效果：相比"硬塞整本书"，RAG 用更少 token 回答更准；同时缓解上下文窗口压力。
  4. 代码助手（Cursor / Copilot Workspace / Claude Code）
    谁在用：开发者。
    解决什么：把整个项目文件读进上下文，让模型跨文件改 bug、生成测试。
    效果：长上下文让"全项目级"修改成为可能；同时倒逼各厂商扩窗口（Claude 1M、GPT-4.1 1M）。
  5. Agent 多步任务的"工作记忆"
    谁在用：Devin、Manus、Claude Computer Use。
    解决什么：Agent 每一步的"思考→行动→观察"结果都回写到上下文，作为下一步推理依据。
    效果：决定了一个 Agent 能连续执行多少步；窗口不够 = Agent 中途失忆、重复试错。

6. 概念辨析

6.1 它是什么 / 不是什么

上下文窗口 是：模型一次推理能"看到"的最大 token 序列，是 Transformer 的硬性架构边界。

上下文窗口 不是：模型的长期记忆、数据库、或可任意扩展的存储。超过它的内容对模型来说就是不存在。

6.2 易混对照表

维度上下文窗口系统提示（System Prompt）RAG长期记忆
作用决定一次推理的"视野"在窗口开头注入人设/规则从外部知识库检索并塞进窗口跨会话保留用户偏好与历史
存储位置GPU 显存（KV-Cache）每次请求都附带向量数据库 + 检索器独立存储（文件/向量库）
占用 token计数上限占用窗口占用窗口只在被调入时占用
怎么区分"我这一眼能看多远""我现在扮演什么角色""需要时去查资料""记住上次说过什么"

6.3 适用前提与失效条件

适用场景：单次任务、文档/对话规模可被窗口容纳、关键信息可放在首尾、对延迟敏感度可接受。
失效条件：
  • 需要的知识总量 > 窗口（如要喂整本百科给模型做问答）——必须用 RAG。
  • 多轮长对话超出窗口——会出现"开头失忆"，需配摘要压缩策略。
  • 把关键事实塞在长上下文中段——触发 Lost in the middle，命中率骤降。
  • 实时性极强 / 成本极敏感——长上下文 = 高延迟 + 高 token 费用，要权衡。
  • 把窗口当"数据库"用——会快速烧光预算，且没有结构化查询能力。

6.4 常见误解

  • 误解 1："1M 上下文 = 模型能像人一样读完百万 token"。纠正：能装下 ≠ 能用好；Lost in the middle 仍然存在，且越长越贵越慢。
  • 误解 2："上下文窗口是软件限制，换更大的 GPU 就能扩"。纠正：限制来自注意力的 O(N²) 二次方增长，硬件只能换算力预算，不能消除数学约束。
  • 误解 3："多轮对话会越来越聪明"。纠正：对话超出窗口后，早期信息对模型不再可见；如果不主动总结/注入，模型会"失忆"。
  • 误解 4："有了长上下文就不需要 RAG 了"。纠正：RAG 不是"替代品"而是"补充品"——RAG 解决"知识更新与精确召回"，长上下文解决"当下任务视野"。

7. 自测题

Q1（概念复述）：用一句话向不懂技术的朋友解释"上下文窗口"。

参考答案：上下文窗口就是大模型一次能"同时看到"的最大文字量——超过这个量的内容模型直接看不见，就像人读书时短期记忆只够装 50 页，第 1 章的线索到了第 80 页就从脑子里掉了。

Q2（机制理解）：为什么上下文窗口不能无限大？请用一个数学原因解释。

参考答案：因为 Transformer 的自注意力要让每个 token 跟窗口内所有其他 token 算关系，计算量是 O(N²) ——N 翻倍，运算量变成 4 倍。这是数学硬约束，加 GPU 也只是换预算，不能消除。

Q3（应用判断）：你想做一个"问答整本公司制度手册"的助手，手册 800 页。该用"塞进上下文"还是"RAG"？为什么？

参考答案：用 RAG。800 页手册 token 量远超任何主流窗口；即使窗口够，也会命中 Lost in the middle 陷阱（用户问的关键词可能正好在中段）。RAG 把手册拆成 chunk 存入向量库，提问时只召回最相关的若干 chunk 塞进上下文，更省、更准、更稳。

Q4（边界辨析）：有人说"有了百万 token 上下文，就不需要 RAG 了"。对吗？请用至少一条理由反驳。

参考答案：不对。RAG 的核心价值是"知识更新"和"精确召回"——长上下文每次都要把所有内容塞进去，token 费用高、延迟大；RAG 只检索相关的几个 chunk，成本低、精度高。另外 RAG 还能引用来源（可解释性）、对接结构化数据库（向量检索 + 元数据过滤），这些是上下文窗口本身做不到的。

Q5（机制应用）：你做一个 Agent，让它"自动查 GitHub issue 并改 PR"。当 Agent 执行到第 30 步时开始"重复试错"，可能的原因是什么？怎么修？

参考答案：很可能是上下文窗口快满了——每一步"思考/观察"结果都堆进窗口，到第 30 步早期指令已被截断，Agent 失去"最初目标感"，开始循环。修法：(1) 主动做上下文摘要压缩，保留关键信息；(2) 把"任务目标"反复注入窗口；(3) 用 KV-Cache 优化降低单步成本；(4) 拆分任务为子任务、每完成一段就清空子任务的中间结果。
