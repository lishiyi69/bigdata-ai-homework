学习目标
  • 准确说出 Agent Skill 的定义与最小组成，理解它与普通 prompt 的区别。

  • 能在具体场景中应用编写最佳实践，并对陌生技能做安全审计。

1什么是 Agent Skill

一个 Skill 在本质上是一个文件夹，其中包含一个名为 SKILL.md 的文件。这个文件至少包含两部分：元数据（name 与 description）和指令正文（告诉智能体如何完成某项任务）。此外，技能还可以捆绑脚本、参考资料、模板等资源。

Anthropic 工程博客给出的定义是：把专业知识打包成可组合（composable）的资源，让通用智能体按需发现并动态加载它们，从而在特定任务上表现得更好——即"把通用智能体变成契合你需求的专业智能体"。

类比 为智能体构建一个 Skill，就像为一位新入职的同事写一份入职指南：不是为每种场景重新造一个专门的智能体，而是把可复用的流程性知识沉淀下来，按需调用。

Skill 与普通 prompt 的关键区别在于按需加载：prompt 是针对一次性任务的对话级指令，而 Skill 是持久化的、跨会话可复用的资源，只有在相关时才会被读入上下文。

2核心原则：渐进式披露

渐进式披露（Progressive Disclosure）是 Agent Skills 之所以"灵活且可扩展"的核心设计原则。它像一本编排良好的手册——先有目录，再有具体章节，最后才是详细附录，让智能体只在需要时加载信息。

这一机制使可捆绑进技能的上下文量"实际上是无界的"：拥有文件系统与代码执行能力的智能体，并不需要把整个技能一次性读进上下文窗口。

层级加载时机内容代价
第一层 · 发现 启动时（始终加载） 每个技能的 name 与 description（元数据） 每个技能约 100 token
第二层 · 激活 任务匹配描述时 完整的 SKILL.md 指令正文 建议 5000 token 以内
第三层及更深 · 执行 按需 被引用的附加文件、可执行脚本与资源 访问前不占用上下文

要点：name 和 description 是智能体决定是否触发某个技能的唯一依据，因此描述必须同时说清楚"这个技能做什么"与"何时使用"。

3SKILL.md 的结构

每个技能都需要一个 SKILL.md 文件，它遵循"两部分"结构：YAML frontmatter（元数据） + Markdown 正文（指令）。

---
name: summarize-changes
description: 总结未提交的改动并标记风险。当用户询问改了什么、需要提交信息或要求审查 diff 时使用。
---

# 技能名称

## Instructions
给智能体的清晰、分步指导。

## Examples
展示该技能的具体使用示例。

必填字段与硬性约束

仅 name 与 description 两个字段为必填，且各自有严格的格式约束：

字段约束
name 最多 64 个字符；只能包含小写字母、数字和连字符；不能包含 XML 标签；不能包含保留字 anthropic、claude。
description 必须非空；最多 1024 个字符；不能包含 XML 标签。最佳实践：同时说明"做什么"与"何时使用"。

其他可选字段（如 allowed-tools、version 等）由具体实现决定，不同平台（Claude Code、Claude API、claude.ai 等）在标准之上有各自的扩展。

4技能目录结构

除 SKILL.md 外，其余一切均可选。常见的组织方式如下：

my-skill/
├── SKILL.md          # 必需：元数据 + 指令
├── scripts/          # 可选：可执行代码
├── references/       # 可选：文档与领域知识
├── assets/           # 可选：模板、资源
└── ...               # 任何其他文件或目录

当技能变复杂时，应把互斥或很少一起使用的上下文拆分成独立文件，并在 SKILL.md 中按名称引用它们。例如 Anthropic 的 PDF 技能把表单填写说明放到 forms.md，主文件保持精简，智能体仅在真正需要填写表单时才去读它。

5为什么捆绑代码

技能可以包含代码，供智能体酌情作为工具执行。打包代码而非让模型"靠 token 生成结果"，有两个核心理由：

  • 效率：某些操作更适合传统代码执行。例如，用 token 生成去给列表排序，远比直接运行排序算法昂贵得多。
  • 确定性可靠性：许多应用要求只有代码才能提供的确定性结果。代码是确定性的，因此该流程一致且可复现。
关键机制 智能体可以运行脚本而不把脚本本身读进上下文——只有脚本的输出进入上下文。因此，指令用于灵活指导，代码用于可靠计算，资源用于事实查询，三者各司其职。

6编写最佳实践

Anthropic 工程博客给出的四条指导原则：

  1. 从评估开始：先在代表性任务上运行智能体，观察它在哪些地方挣扎或缺少上下文，再有针对性地、渐进地构建技能来填补这些能力缺口。
  2. 为规模化构建结构：当 SKILL.md 变得臃肿时，把内容拆分成独立文件并引用；互斥或很少共用的上下文分开存放能减少 token 消耗。代码既可当可执行工具，也可当文档——要写清楚智能体应直接运行脚本，还是把脚本读进上下文作参考。
  3. 从智能体的视角思考：观察智能体在真实场景中如何使用技能，留意意外的行为轨迹或对某类上下文的过度依赖，据此迭代。尤其要重视 name 与 description 的质量。
  4. 与智能体一起迭代：让智能体把成功做法与常见错误沉淀进技能的可复用上下文和代码；若它用技能时跑偏，让它自我反思问题出在哪。这能帮你发现智能体真正需要什么上下文，而不是靠事前猜测。

7安全注意事项

技能通过指令和代码赋予智能体新能力，这也意味着恶意技能可能引导智能体以与声明用途不符的方式调用工具或执行代码。官方建议：

  • 仅使用可信来源的技能——自己创建的，或从 Anthropic 官方获取的。
  • 使用陌生技能前彻底审计：阅读其中捆绑的所有文件（SKILL.md、脚本、图片等），特别留意代码依赖与捆绑资源。
  • 从外部 URL 拉取数据的技能风险更高——拉取到的内容可能包含恶意指令。
  • 把安装技能当作安装软件一样谨慎对待。
